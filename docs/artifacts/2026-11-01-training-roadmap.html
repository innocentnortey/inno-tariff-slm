How we train the tariff specialist

We are teaching a small open model one job: given a product description and eight candidate US tariff codes, pick the code Customs would assign and name the fact that decided it, or ask for the fact that is missing. This page walks through ten steps: nine to build, train, and publish the model, and a tenth that tests the hypothesis behind the whole project, that a trained small model earns its place next to a well-prompted general model with retrieval.

No model has been trained yet. Every number marked Measured comes from the data check of October 30, 2026, as corrected by the label review of November 1, 2026. Everything else is a plan.

The target: one behavior, shown first

The model does one thing. Here is that thing as an input and an output, using a real case from the project's research: CBP ruling NY N346508 placed a 100% silk scarf in the 1.2% duty line, while other silk scarves take 3.9%.

Input Description: "100% silk scarf, hemmed edges."
Candidates: eight HTS lines from the same part of the schedule tree, including 6214.10.10.00 (silk scarves containing at least 70% silk, 1.2%) and 6214.10.20.00 (other silk scarves, 3.9%). Schedule wording is shortened here.
↓ the model reads the text and compares the candidates
Output 
{"decision": "SELECT", "code": "6214.10.10.00",
 "deciding_attribute": {"dimension": "fiber_content", "value": "100% silk"},
 "runner_up": "6214.10.20.00"}

The cited value, 100% silk, appears word for word in the description. That is what "grounded" means in the spec.

Input (illustrative, written for this page) Description: "Silky scarf, 90 cm square."
Candidates: the same eight lines.
↓ the description never states fiber content, and fiber content separates the top two candidates
Output 
{"decision": "NEED_INFO", "code": null,
 "deciding_attribute": {"dimension": "fiber_content", "value": null},
 "runner_up": null}

"Silky" is a texture, not a fiber. A model that picks a code here is guessing, and a wrong code means a wrong duty on every shipment. Asking is the correct answer.

Why this behavior, and what it does not prove

Frontier models are weak at full 10-digit classification. In the ATLAS benchmark (arXiv 2509.18400), GPT-5-Thinking got 25.0% fully right on 200 CBP rulings, and the authors' fine-tuned LLaMA-3.3-70B got 40%. That result suggests domain training can help. It is a reason to run an experiment, not a settled answer, for three reasons:

  • The trained model was 70B parameters. We plan 1.7B–4B.
  • ATLAS did not compare against a well-built retrieval (RAG) system. It lists retrieval augmentation and smaller models as future work.
  • It did not test our contract: choose among eight candidates, or ask for the missing fact.

A small model that learns the narrow skill of comparing close candidates and refusing to guess is a testable claim. "A RAG system cannot do this" is a stronger claim that the evidence does not support, and this project does not make it. Step 10 is where we test the weaker, defensible claim.

What stays outside the model. Finding the candidates (retrieval), duty rates and arithmetic, reading attributes out of invoices, and the final decision (a licensed person). The model trains on the choice between candidates only. Retrieval is weak today (plain BM25 finds the right code in the top 8 for 4% of test rulings), so the plan gives every model the same eight candidates and measures retrieval separately.

Step 1

Finalize the behavior and hand-review 50 labels

What it does
Locks the one-to-two-sentence behavior spec and checks that the answers we will train on are correct.
How it works
The "deciding attribute" for each example is computed by a lexicon: a hand-written list that maps schedule wording (such as "Of cotton" or "For women") to a dimension (fiber_content, gender_age, and so on). No model is involved. Because the lexicon sets both the attribute and the NEED_INFO labels, a lexicon bug becomes a training bug. The review checks those derived labels, not the tariff codes, which come from CBP and are trusted. For each item it asks: do the two schedule lines differ on the named attribute, does the description state it, and if not, is it truly absent?
Status
Measured Done on November 1, 2026 by Claude, at Innocent's request. 100 items were read in two rounds, and every item was pattern-audited. Seven error patterns were fixed in the build code, not by editing labels; the worst was that cited words only had to mention the attribute, not separate the two lines. 83 items whose description contradicts CBP's code are dropped. Record: docs/data/label-review-2026-11-01.md.
Why it comes first
The first draft already caught two lexicon bugs: "man-made" was read as a gender word, and "pigskin" as "ski". A model trained on those labels learns the bugs.
Output
A signed behavior spec and a reviewed label sample with a count of errors found and fixed.
GateInnocent signs the spec, and the label review finds no unfixed lexicon error pattern. The second half is met; the spec sign-off is open.
Step 2

Build the evaluation harness before training

What it does
Scores any model, including a baseline, a frontier model, or our tuned model, against the same test items with the same rules.
How it works
Two layers. The behavioral check is code: valid JSON, the right code, the right dimension, and a cited value that appears in the description. The judge is a model that answers two yes/no questions for each SELECT: is the attribute stated, and does it separate the chosen code from the runner-up. We calibrate the judge against about 20 hand labels before it counts, and save its raw output as JSONL.
Output
eval.py --model … --eval-set … as a single command that prints the metrics table and writes the judge JSONL.

What the harness already measured

Measured on the reviewed 221-item test set, exact 10-digit match on items that need a code:

Non-model baseline10-digit accuracy
Random pick among 811.4%
Keyword overlap16.3%
Attribute rules37.5% (spec pass 24.9%; caught 13.5% of ask-when-unsure cases; over-asked on 7.1%)

Any trained model must beat these to mean anything. The rules baseline rose from 20.5% after the label review, mostly because it shares the improved lexicon, so its attribute scores are optimistic. Its code accuracy is scored against CBP's codes, so about 38% is a real bar for the tuned model.

Small test set. The test set has 110 decidable items. By my estimate, a pass rate near 50% on 110 items carries roughly ±10 points of sampling noise at 95% confidence. A "+20 points" claim survives that; a "+5 points" claim does not. Report the counts next to every percentage.
GateThe harness runs end to end on the three baselines and one judge calibration set, and the judge agrees with the hand labels well enough to trust (agree on the threshold before looking at results).
Step 3

Run the prompt-ceiling ablation

What it does
Answers "could a good prompt do this without training?" with a measurement.
How it works
Two frontier model families (proposed: Anthropic and OpenAI) × three prompt strategies (zero-shot, few-shot, structured chain-of-thought) × at least 30 scenarios per cell. Each model sees the same eight candidates and is scored by the step 2 harness. That is at least six cells and 180 scored answers.
Where it runs
On the VPS. The API keys live there, and this Mac has none.
Output
A report with one number per cell and the best prompt's failure examples.
Result, November 1, 2026. Measured Best cell: Claude Opus 5.5 with the structured reasoning prompt, 86.0% spec adherence and 87.9% robustness; GPT-5.6 Sol's best was 82.8% and 67.2%. The three strategies land within 1.3 points (Opus) and 4.5 points (GPT) of each other: a plateau. The failure that survives every prompt is choosing between a residual "Other" line and its named sibling (13 of the best cell's 22 failures); an embedded instruction also makes GPT adopt the wrong code on 6–10 of 14 items. No absolute spec bar was set before the run, so that bar is the open decision. Report: docs/evals/prompt-ceiling-2026-11-01.md.
GateThere are two possible results, and both are acceptable. If the best prompt fails the spec in ways a small model could learn, fine-tuning is justified. If the best prompt already passes reliably, we say so and narrow the behavior (for example, only the harder "close siblings" cases).
Step 4

Build and filter the training data

What it does
Turns public CBP rulings into training examples in the exact input/output format from the target section.
Where the answers come from
The ruling's code and the USITC schedule. Never from a teacher model. A teacher model may write a short explanation afterward, and we keep it only if its code and attribute match the labels.

One ruling becomes one example

  1. Filter. Keep rulings with exactly one 10-digit code that exists in today's schedule, in Chapters 61, 62, and 64 (knit apparel, woven apparel, footwear). Drop descriptions that mention HTS numbers or code digits, because those leak the answer.
  2. Split by date. Train on rulings up to 2022, tune on 2023, test on 2024–2025. Remove any training description that duplicates a dev or test description. Test rulings postdate much of what frontier models trained on, which limits memorization.
  3. Build candidates. The correct code plus its seven nearest siblings in the schedule tree (same 8 digits first, then 6, then 4), shuffled with a fixed seed.
  4. Compute the deciding attribute. Find the first level where the correct code's schedule path differs from its nearest sibling's, and map that wording to a dimension with the lexicon.
  5. Create NEED_INFO cases without inventing ambiguity. A natural case is a ruling whose correct line names a positive attribute (such as "For women") that the description never states. An ablated case removes the attribute words from a decidable item. A residual line ("Other") is decided by absence, so it is never NEED_INFO.
  6. Check for leakage and drift. Exact-duplicate removal across splits, obsolete codes dropped, ruling IDs kept for provenance.

Why Chapters 61, 62, and 64

Among all chapters they hold the most rulings with currently valid codes, and their codes split on attributes a person can name: fiber, knit or woven, intended wearer, upper material. Footwear averages about 42 ten-digit siblings per 6-digit subheading, so the choice between close candidates is real.

What we cannot publish yet

The public copy of the rulings on Hugging Face (orlandowhite/hts-cross-rulings) has no license. We publish our derived dataset with provenance to CBP and do not re-upload that copy. We confirm CBP's terms before publishing anything derived.

GateThe build is reproducible from one script and a seed, no description appears in two splits, and the step 1 label review is passed.
Step 5

Fine-tune the first model with QLoRA

What it does
Adjusts a small open model so that, for these inputs, it produces the JSON from the target section.
How it works
QLoRA keeps the base model's billions of weights frozen in compressed 4-bit form and trains a small set of extra weights (adapters) on top. That is why a 1.7B-parameter model fits on one 24 GB GPU. Training uses response-only loss: the model is graded only on the JSON it writes, not on re-predicting the prompt.

The starting recipe

These are starting estimates, not measured settings.

Two runs, in this order

  1. Smoke run. A few dozen examples through generate → train → evaluate. The goal is a working loop with real numbers, however poor. A broken pipeline is cheaper to find here than after a full run.
  2. First real run. The full training pool at the starting recipe, scored by the step 2 harness.

Compute is one A100 or H100 on Modal, RunPod, or Colab. Gauntlet covers the cost. The plan expects each 1.7B run to take well under an hour, but that is an estimate until the smoke run times it.

GateThe smoke run completes the whole loop and produces a scored checkpoint, and the training prompt is byte-identical to the evaluation prompt.
Step 6

Compare base against tuned

What it does
Produces the headline result: the same eval set, the same prompt template, the untuned base model against the tuned one.
How it works
Run eval.py on both. Report every metric from the scorecard with counts. Also include the frontier-with-same-candidates result from step 3, so the reader sees where the small model lands relative to a large one.
What we expect to learn
Whether the tuned model asks when it should (NEED_INFO recall), stays quiet when it should (over-asking), and cites only what the description says (grounding).
GateTuned beats base on spec pass rate by at least 20 points. If it does not, the failure condition applies: report no gain, diagnose, and narrow the behavior. We do not tune hyperparameters to rescue a null result.
Step 7

Diagnose a failure and fix it with data (v2)

What it does
Shows we understand why the model fails, by fixing one failure through the training data and measuring the change.
How it works
Read the tuned model's wrong answers and group them by cause. For each group, ask what the data failed to teach. Pick one failure and change the data, then retrain and score again.

Example of the loop (hypothetical until step 6 runs)

  • Symptom: the model picks a code on "silky scarf" items instead of asking.
  • Diagnosis: the training set has few natural NEED_INFO cases for fiber content, so the model has seen the pattern rarely.
  • Data fix: add ablated NEED_INFO copies for fiber content from the training rulings.
  • Check: retrain; fiber-content NEED_INFO recall rises, and over-asking on decidable items stays at or below 0.1.
GateOne named failure mode, one data change, and a before/after score on the same eval set with the over-asking metric reported alongside.
Step 8

Run the data-efficiency curve

What it does
Answers "how little training data is enough?" with a curve.
How it works
Train on nested subsets (each one contains the smaller ones): for example 500, 1,000, 2,000, and 4,000 rulings. Score every checkpoint on the same held-out set and plot spec pass rate against N. The early submission needs at least two points; the final needs at least four.
Output
The curve and a justified minimum N: the smallest size that clears the bar from step 6.

If the curve is flat from the first point, the behavior is easy for this model and the data is not the lever. If it keeps climbing at 4,000, we say the minimum N was not found and show how far the 5,865 available rulings extend it.

Step 10

Test the hypothesis: does the small model earn its place?

Steps 1–9 show whether the tuned model beats its own untuned base. They do not show whether anyone needs it. A retrieval (RAG) system already feeds a general model the schedule text, notes, and similar past rulings, and that model reasons over them. For many products, such as a blouse with a matching ruling, that may be enough. Step 10 tests the claim this project can defend:

Hypothesis. Within a retrieval-based system, a trained small tariff specialist chooses between close candidates, cites real evidence, and asks for missing facts more reliably or more cheaply than a well-prompted general model.
What it does
Compares three decision models on identical inputs, so a difference in results comes from the model and nothing else.
How it works
Give the same held-out products, the same eight candidates, the same schedule text, and the same retrieved rulings to each arm. Score all arms with the step 2 harness.

The three arms

ArmModelWhat it answers
AWell-prompted general model (the best cell from step 3)What retrieval plus prompting already achieves.
BSmall model before trainingHow much of the result is the base model, not our training.
CThe same small model after trainingWhat the training adds.

The comparison that decides the hypothesis is C against A. The comparison of C against B (step 6) shows that training worked at all.

Two ways to supply the candidates

  • Gold code forced into the eight. This isolates decision quality. It cannot show end-to-end performance, because real retrieval often misses the right code (plain BM25 hits 4% at eight on our test rulings).
  • Candidates from the real retriever. This shows end-to-end performance. A miss counts against retrieval recall, never against the model, so a missing candidate does not look like a reasoning failure.

Report both, in separate tables.

Where the hypothesis should show or fail

Easy items hide the difference: a matching precedent lets any model succeed, and a clear numeric threshold is better checked in ordinary code. The training hypothesis is strongest where there is no exact matching ruling, several similar precedents exist, and the candidates differ subtly. For example, a hooded garment with a zipper can resemble both a shirt and a sweatshirt; the model must decide which facts control the code, which similarities are incidental, and whether the description says enough.

So score a hard slice separately: test items where the retriever returns no ruling for the same product, and items whose candidates share all but one attribute. The slice rule is written down before any model sees the test set.

What gets measured

MeasureWhy it matters for this hypothesis
Spec pass rate, 10-digit accuracyDoes C match or beat A?
Unsupported selections (false confidence)Does the model pick a code when the deciding fact is missing?
NEED_INFO recall, and whether the question names the right missing factIs the clarification useful, not just present?
Over-askingA model that always asks looks good on recall and is useless.
GroundingDoes it cite facts the description states?
Cost and latency per decisionA small model can win on cost even when it ties on accuracy. Count hosting and utilization, not only token price.

How to read the result

If you seeThe claim we can make
C beats A on the hard slice by more than the noiseTraining improves judgment on close calls. This is the strongest result.
C ties A and costs less per decision, including hostingThe small model earns its place on cost. Say that the accuracy did not improve.
A meets the behavior bar and beats CRetrieval plus prompting is enough. Narrow or reconsider the training target and report the finding. A privacy argument can still justify a small deployment, but it does not require fine-tuning.
C beats B but loses to A, with no cost advantageTraining worked and the specialist is still not needed.

With 110 decidable test items (see the step 2 note on noise), most of these differences must be large to count. Commit the margin that counts as "ties" before the first run, and report counts beside every percentage.

Open design question: should the model see retrieved rulings? A fair three-arm comparison gives every arm the same retrieved rulings, which means the trained model's prompts must include them. Our current training format has candidates and schedule text only. Adding retrieved rulings changes the example format in step 4, so it is cheaper to decide now than to retrain after step 5. I recommend a two-stage plan: run the first comparison on the current format (candidates and schedule text for all arms), then, if the result is close or ambiguous, add retrieved rulings to all three arms and retrain. Innocent decides.
GateThe report states the hypothesis, shows arms A, B, and C on identical inputs with retrieval scored separately, includes the hard slice and cost with hosting, and ends with one sentence from the table above that the numbers support. If A wins, we say so.

What can go wrong

Retrieval is the bottleneck

Plain BM25 finds the right code in the top 8 for 4% of test rulings. The project avoids this by handing every model the same eight candidates, but the product claim ("an analyst that finds the code") depends on retrieval we have not built. Say so in the Brainlift.

Labels come from our own lexicon

The attribute labels and the rules baseline share one lexicon, so agreement between them proves little. The 50-label hand review and the judge calibration are the independent checks.

Small dev and test sets

143 dev rulings and 197 test rulings give wide error bars. Report counts, avoid claims smaller than the noise, and use the staff held-out set as the second opinion.

Prompting and retrieval may already be enough

If step 3 shows a strong frontier prompt passes, or step 10 shows a general model with retrieval matches the tuned model, fine-tuning adds little. The plan treats that as a valid finding and narrows the behavior instead. The project does not claim that RAG cannot do this.
