# Tariff research roadmap: does domain fine-tuning improve 10-digit classification?

Started 2026-11-01. Owner of decisions: Innocent. Status marks: `[ ]` open, `[x]` done (with evidence), `[~]` in progress.

**Hypothesis.** Domain fine-tuning improves a small model's ability to assign the correct 10-digit HTSUS code to a
product description, measured against the same base model, on a benchmark that does not hand it the answer.

**What changed from the earlier experiment.** The earlier benchmark (`docs/evals/step10-head-to-head-2026-11-01.md`)
always put the gold code among eight supplied candidates and covered chapters 61, 62 and 64 only. It measured
choosing between close codes, not classification. Its files, runs and published model stay as historical evidence;
none of its numbers are used here as evidence of full-classification performance.

## Phase 1 — Establish the right benchmark

- [x] Read the existing research and results; record what carries over (`docs/research/`, `docs/evals/`, `docs/data/`).
- [x] Verify ATLAS (arXiv 2509.18400): 18,731 CROSS rulings, random 18,254/200/200 split, GPT-4o-mini-written
      descriptions made while seeing the code, closed-book prompt, scored by exact 10-digit, 6-digit and average
      digits. The `flexifyai` repos are now private; a public Apache-2.0 copy with the same split is at
      `Dayanand314Krishna/cross_rulings_hts_dataset_for_tariffs` @ `0a66ad34` (SHA-256s in `docs/evals/benchmark-protocol.md`).
- [x] Fetch post-corpus CROSS rulings: 3,803 rulings N351546–N365822, 2025-07-28 → 2026-10-09
      (`scripts/fetch_cross_recent.py`, run on the VPS; the search API is reCAPTCHA-gated, the single-ruling endpoint is open).
- [x] Write the benchmark protocol (`docs/evals/benchmark-protocol.md`): two tracks, inputs, scoring, ATLAS differences.
  - **Track A, ATLAS reproduction:** ATLAS's 200 test items, their exact question, closed-book; their metrics.
  - **Track B, primary (open-set, end-to-end):** fresh rulings, product facts only, any code in the current HTSUS;
    retrieval candidates generated by our pipeline, and retrieval misses count as errors.
- [x] Build retrieval: TF-IDF + dense (bge-base) over earlier rulings and HTSUS lines; recall@20 dev 74.7%, test 80.0%.
- [x] Run baselines on dev, then freeze (dev `rag`: retrieval-only 36.7%, base 42.0%, Opus 71.3%; Track A Opus 41.0%, base 0%): retrieval-only vote, base small model (closed-book and RAG), Claude Opus 5.5
      (closed-book and RAG), and one other frontier family if the budget allows.
- [x] Freeze the protocol and the success criteria below before any tuned model is evaluated (2026-11-02).

**Pre-registered success criteria (Track B final test, frozen before training).**
1. *Supports the hypothesis:* tuned exact 10-digit accuracy exceeds the base model's, with identical retrieval context
   and prompt, by at least 5 points, and the paired bootstrap 95% interval of the difference excludes 0.
2. *Useful system (secondary):* tuned accuracy exceeds the retrieval-only baseline, interval excluding 0.
3. *Frontier comparison (reported, not a criterion):* tuned minus Opus 5.5 RAG, with its interval. Beating it is a
   result to report, not a goal to tune for.

## Phase 2 — Prepare trustworthy training and evaluation data

- [x] All-chapter cleaned corpus: one primary 10-digit code (chapters 01–97), code valid in the current HTSUS, ruling
      not revoked; drop multi-product rulings.
- [x] Descriptions taken from the ruling's own facts section, with sentences naming codes, headings, notes or the
      requester's proposed classification removed; leakage check by code-digit and heading-text patterns.
- [x] Remove exact and near-duplicates; drop conflicting-label groups; remove ATLAS test rulings from train and from
      every retrieval index.
- [x] Splits by date (19,508 train · 300 dev · 500 test, built on Modal `train/modal_build.py`): train ≤ 2023; dev 2024 → Jul 2025; final test = fresh post-corpus rulings (never inspected).
      The earlier ch. 61/62/64 test set stays historical.
- [ ] Fidelity audit on a dev sample: does the description keep the deciding facts, and does it reveal the answer?
- [ ] Read baseline failures; fix only the data problems that cost accuracy (missing facts, close codes, legal notes,
      unsupported guessing).
- [x] Training prompts built exactly like inference prompts (same retrieval, leave-one-out for the example itself).
- [ ] Version datasets: checksums and build commands in `docs/data/benchmark-v2.md`.

**Goal added 2026-11-02 (Innocent):** the tuned model should beat Opus 5.5 on the final test, with three training
runs in total. Recorded as an amendment in the protocol; criteria 1–2 are unchanged.

## Phase 3 — Train and evaluate

- [x] Choose model and method: Qwen3-4B-Instruct-2507, bf16 LoRA r=16 on a Modal H100 (`train/modal_openset.py`).
- [x] Try 1: full train set (19,508), 1 epoch: dev 57.7% exact (base 42.0%, Opus 71.3%); answers from the candidate
      list 96% of the time; 0% when retrieval misses. (First run killed by the Modal spend limit; rerun 2026-11-02.)
- [x] Try 2: temporal retrieval + 1,931 recent rulings + 19,831 schedule lines: dev 59.3% (+1.7 over try 1, CI −1.0 to
      +4.3); 2.6% when retrieval misses; closed-book ATLAS 0.5%.
- [x] Try 3 (Codex-reviewed recipe, Innocent's OK for $55 of Opus): continue try 2's adapter at lr 5e-5 on 488
      Codex-verified Opus rationales (labels from CBP; 1,500 hinted generations + 497 repairs, judge rejected 50/50
      controls; $50.29) ×3, 2:1 code-only replay, and 6,480 backfilled CROSS rulings (11,740 fetched, N200000–N341600
      partly; resumable). Dev 59.7% (selected); forced reasoning 48.0% (rejected). Data `data/benchmark_try3/`.
- [x] One final-test evaluation (2026-11-02): tuned 59.8%, base 42.0%, retrieval-only 38.0%, Opus 71.6%; Track A tuned 0.0%, Opus 41.0%.
- [x] Report accuracy (10-, 8-, 6-digit), missing-information behaviour where evaluated, cost and latency.
